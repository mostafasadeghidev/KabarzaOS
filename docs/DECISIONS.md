# Decision log

Each entry records a decision and, more importantly, why it was made.
Some IDs are cited from code comments — do not renumber them.

---

## D-004 — Stack

Next.js (App Router) with TypeScript, PostgreSQL, Drizzle, Tailwind with
shadcn/ui, Vitest.

**Why:** pages and server logic live in one deployable unit, so there is
no separate API server to keep in sync. TypeScript end to end means the
same validation schema serves both the form and the action.

---

## D-005 — `app/api/` stays thin

Route handlers parse input and delegate. They contain no business rules.

**Why:** the same operation must behave identically whether it arrives
from a form, a route, or a scheduled job. Logic in a handler is reachable
by exactly one of those.

---

## D-006 — Logic in the domain layer, not in components

**Why:** a rule inside a component can only be tested by rendering. In
`src/domain` it is a pure function with a table of cases.

---

## D-007 — Tests from day one

Unit tests for domain logic, integration tests against a real Postgres.

**Why:** the defects that actually shipped in this codebase were never
"the logic is wrong" — they were "each part is right, the wiring is
wrong". Only integration tests catch those.

---

## D-008 — Background work is separate

Reminders, upcoming meetings, abandoned timers, the daily digest and
cleanup all run from a single scheduler tick, not from request handlers.

**Why:** a request must not depend on work that can be slow or fail.

---

## D-009 — Deployment with Docker/Coolify

Services: `app` (Next.js) · `db` (Postgres) · `storage` (S3-compatible) ·
`cron` (scheduler tick).

**Non-negotiables:**

- Uploaded files (receipts, attachments) are **never stored on the
  container filesystem** — they are wiped on every deploy. They go to
  S3-compatible storage. This is the single most common mistake.
- Migrations run at startup, never by hand.
- Postgres is reachable only on the internal network.
- At least 4 GB of RAM on the build host (Next.js build).

## D-014 — Three data-model decisions

1. **`scope` everywhere from day one** (finance, projects, tasks), default
   `company`.
   *Why:* adding the column now is cheap; adding it later means rewriting
   every report.

2. **Authorization is enforced in the domain layer, not with RLS.**
   *Why:* one enforcement point that the UI, the API and any future agent
   all pass through.
   *Condition:* no query may bypass the domain layer (R-ARCH-01).

3. **`tags` stays polymorphic**, with `type` constrained by a check.
   *Why:* adding a new status without a migration is worth the
   indirection.

---

## D-016 — Secrets are generated by the container, not required as input

`SESSION_SECRET` and `CRON_SECRET` are generated on first boot and kept in
a volume.

**Why:** the session key must be both random and stable across restarts. A
fixed default in the compose file would make it guessable, and generating
it per boot would sign everyone out on every deploy. A file on a volume
satisfies both. A variable supplied by the operator always wins.

---

## D-017 — `docker-compose.yml` is the production file

Development services live in `docker-compose.dev.yml`.

**Why:** deployment tools and `docker compose` itself pick up the default
name with no flag, so deploying is `docker compose up -d --build`.
